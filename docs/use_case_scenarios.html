SKENARIO USE CASE (AKTOR PENGGUNA)
Sistem Reservasi & Pelaporan Fasilitas Kampus - PPK 2026

Tabel UC-01: Melihat Daftar Fasilitas

Use CaseUC-01: Melihat Daftar Fasilitas
Pre-condition
  • • Pengunjung/Pengguna telah membuka web platform fasilitas kampus. • Sistem telah terhubung ke database fasilitas.
Post-condition
  • • Sistem menampilkan daftar fasilitas yang tersedia kepada pengunjung/pengguna.
Basic path
  1. Pengguna mengakses halaman/menu fasilitas. 2. Sistem mengambil data fasilitas dari database. 3. Sistem menampilkan daftar fasilitas beserta informasi seperti nama, tipe, lokasi, kapasitas, dan deskripsi. 4. Pengguna dapat melihat daftar fasilitas yang tersedia.
Alternative path
  • • Pengguna dapat melanjutkan ke proses pencarian fasilitas berdasarkan kebutuhan.
Exceptional path
  • • Jika data fasilitas tidak tersedia, sistem menampilkan notifikasi bahwa belum terdapat fasilitas yang dapat ditampilkan.

Tabel UC-02: Mencari Fasilitas

Use CaseUC-02: Mencari Fasilitas
Pre-condition
  • • Pengunjung/Pengguna telah membuka halaman daftar fasilitas. • Sistem telah terhubung ke database fasilitas.
Post-condition
  • • Sistem menampilkan fasilitas yang sesuai dengan kata kunci atau filter pencarian.
Basic path
  1. Pengguna memasukkan kata kunci pencarian atau memilih filter. 2. Pengguna dapat menggunakan filter berdasarkan tipe, lokasi, atau kapasitas. 3. Sistem memproses kata kunci/filter yang diberikan. 4. Sistem menampilkan daftar fasilitas yang sesuai dengan kriteria pencarian.
Alternative path
  • • Pengguna mengosongkan kata kunci/filter. • Sistem mengembalikan tampilan ke seluruh fasilitas yang tersedia.
Exceptional path
  • • Jika tidak terdapat fasilitas yang sesuai dengan kriteria pencarian, sistem menampilkan notifikasi: "Fasilitas tidak ditemukan".

Tabel UC-03: Melihat Ketersediaan Fasilitas

Use CaseUC-03: Melihat Ketersediaan Fasilitas
Pre-condition
  • • Pengunjung/Pengguna telah melihat daftar fasilitas. • Pengguna telah memilih fasilitas yang ingin diperiksa. • Sistem memiliki data jadwal reservasi fasilitas.
Post-condition
  • • Sistem menampilkan status ketersediaan fasilitas berdasarkan tanggal dan slot waktu yang dipilih tanpa menampilkan data pemohon lain.
Basic path
  1. Pengguna memilih salah satu fasilitas. 2. Pengguna memilih tanggal yang ingin diperiksa. 3. Sistem menampilkan slot waktu operasional 07.00–20.00 dengan interval 30 menit. 4. Sistem memeriksa data reservasi pada fasilitas tersebut. 5. Sistem menampilkan status setiap slot sebagai Tersedia atau Tidak Tersedia.
Alternative path
  • • Pengguna memilih tanggal lain. • Sistem memperbarui status ketersediaan berdasarkan tanggal yang dipilih.
Exceptional path
  • • Jika terjadi gangguan saat mengambil data jadwal, sistem menampilkan notifikasi bahwa data ketersediaan tidak dapat ditampilkan dan meminta mencoba kembali.

Tabel UC-04: Melakukan Registrasi Akun

Use CaseUC-04: Melakukan Registrasi Akun
Pre-condition
  • • Pengguna belum memiliki akun dan berada di halaman Registrasi.
Post-condition
  • • Data akun baru berhasil tersimpan di database dengan status Menunggu Verifikasi Admin dan password terenkripsi.
Basic path
  1. Pengguna membuka form Registrasi Akun. 2. Pengguna mengisi data lengkap (Nama Lengkap, Email Kampus, Password, Konfirmasi Password, dan Kategori: Mahasiswa/Dosen/Staf). 3. Pengguna menekan tombol "Daftar". 4. Sistem melakukan validasi format data di sisi client dan server. 5. Sistem menyimpan data akun baru ke database dengan status 'Menunggu Verifikasi Admin'. 6. Sistem menampilkan pesan bahwa registrasi berhasil dan akun menunggu verifikasi Admin sebelum dapat login, lalu mengarahkan pengguna ke halaman Login.
Alternative path
  • • Pada langkah 2, pengguna menekan tautan "Sudah punya akun? Login di sini", sistem langsung mengarahkan pengguna ke halaman Login.
Exceptional path
  • • Pada langkah 4, jika email sudah pernah terdaftar, sistem menolak pendaftaran dan menampilkan pesan: "Email sudah terdaftar". • Pada langkah 4, jika password dan konfirmasi password tidak cocok atau ada field kosong, sistem menampilkan pesan peringatan validasi pada form.

Tabel UC-05: Melakukan Login & Logout

Use CaseUC-05: Melakukan Login & Logout
Pre-condition
  • • Untuk Login: Akun pengguna telah terdaftar dan berstatus aktif. • Untuk Logout: Pengguna sedang berada dalam sesi login aktif.
Post-condition
  • • Untuk Login: Sesi autentikasi aktif dibuat dan pengguna masuk ke Dashboard. • Untuk Logout: Sesi autentikasi dihapus dan hak akses khusus dicabut.
Basic path
  1. Pengguna membuka halaman Login. 2. Pengguna memasukkan Email dan Password, lalu menekan tombol "Login". 3. Sistem memverifikasi kredensial akun ke database. 4. Sistem membuat sesi pengguna dan mengarahkan ke halaman Dashboard Utama. 5. Saat selesai menggunakan sistem, pengguna menekan tombol "Logout". 6. Sistem menghancurkan (destroy) sesi login dan mengarahkan kembali ke halaman Login.
Alternative path
  • -
Exceptional path
  • • Pada langkah 3, jika kombinasi email atau password salah, sistem menampilkan notifikasi error: "Email atau password salah". • Pada langkah 3, jika akun belum diverifikasi oleh Admin, sistem menampilkan pesan: "Akun Anda masih menunggu verifikasi Admin".

Tabel UC-06: Mengajukan Reservasi Fasilitas

Use CaseUC-06: Mengajukan Reservasi Fasilitas
Pre-condition
  • • Pengguna telah berhasil login ke sistem. • Fasilitas yang dipilih berstatus aktif (tidak sedang dalam perbaikan).
Post-condition
  • • Pengajuan reservasi tersimpan di database dengan status Menunggu Persetujuan.
Basic path
  1. Pengguna memilih fasilitas yang ingin dipesan dari katalog. 2. Pengguna mengisi form reservasi: memilih tanggal penggunaan, Start Time, End Time, dan menuliskan tujuan penggunaan. 3. Pengguna menekan tombol "Ajukan Reservasi". 4. Sistem melakukan validasi server-side: a. Memeriksa jam berada dalam rentang 07.00–20.00. b. Memeriksa waktu kelipatan slot 30 menit. c. Memeriksa tidak ada bentrok jadwal dengan reservasi yang disetujui. 5. Sistem menyimpan data ke tabel Reservations dengan status Menunggu Persetujuan. 6. Sistem menampilkan notifikasi sukses dan mengarahkan ke halaman Riwayat Reservasi.
Alternative path
  • • Pada langkah 2, pengguna dapat membatalkan pengisian dan kembali ke halaman katalog tanpa menyimpan data.
Exceptional path
  • • Pada langkah 4, jika slot waktu yang dipilih sudah terpesan/bentrok, sistem menolak dan menampilkan pesan: "Slot waktu tersebut sudah terisi, silakan pilih waktu lain". • Pada langkah 4, jika waktu di luar jam operasional (sebelum 07.00 / setelah 20.00) atau bukan kelipatan 30 menit, sistem menampilkan pesan error validasi waktu.

Tabel UC-07: Melihat Riwayat & Status Reservasi

Use CaseUC-07: Melihat Riwayat & Status Reservasi
Pre-condition
  • • Pengguna telah login ke dalam sistem.
Post-condition
  • • Daftar seluruh reservasi milik pengguna ditampilkan lengkap beserta status dan detailnya.
Basic path
  1. Pengguna memilih menu "Riwayat Reservasi". 2. Sistem mengambil seluruh data pemesanan milik pengguna yang bersangkutan dari database. 3. Sistem menampilkan tabel daftar reservasi yang memuat: Fasilitas, Tanggal, Jam, Tujuan, dan Badge Status (Menunggu Persetujuan, Disetujui, Ditolak, Dibatalkan). 4. Pengguna mengklik salah satu baris reservasi. 5. Sistem menampilkan modal pop-up detail lengkap reservasi (termasuk alasan penolakan jika status ditolak).
Alternative path
  • • Pada langkah 3, pengguna dapat menggunakan fitur filter berdasarkan status (misal: hanya melihat yang 'Disetujui').
Exceptional path
  • • Pada langkah 2, jika pengguna belum pernah membuat reservasi sama sekali, sistem menampilkan pesan: "Belum ada riwayat reservasi".

Tabel UC-08: Membatalkan Reservasi

Use CaseUC-08: Membatalkan Reservasi
Pre-condition
  • • Pengguna telah login. • Reservasi yang dipilih milik pengguna sendiri dan berstatus Menunggu Persetujuan atau Disetujui.
Post-condition
  • • Status reservasi di database berubah menjadi Dibatalkan dan slot waktu jadwal kembali berstatus Tersedia.
Basic path
  1. Pengguna membuka halaman "Riwayat Reservasi". 2. Pengguna memilih reservasi aktif yang ingin dibatalkan dan menekan tombol "Batalkan". 3. Sistem memeriksa aturan batas waktu pembatalan (deadline rule). 4. Sistem menampilkan dialog konfirmasi pembatalan. 5. Pengguna menekan tombol "Ya, Batalkan". 6. Sistem memperbarui status reservasi menjadi Dibatalkan dan melepaskan slot jadwal di database. 7. Sistem menampilkan notifikasi sukses pembatalan.
Alternative path
  • • Pada langkah 4, pengguna menekan tombol "Batal / Kembali", sistem menutup dialog konfirmasi dan tidak melakukan perubahan status.
Exceptional path
  • • Pada langkah 3, jika waktu pembatalan sudah melewati batas toleransi yang ditentukan, sistem menolak aksi dan menampilkan pesan: "Reservasi tidak dapat dibatalkan karena sudah melewati batas waktu minimum".

Tabel UC-09: Membuat Laporan Kerusakan

Use CaseUC-09: Membuat Laporan Kerusakan
Pre-condition
  • • Pengguna telah login ke dalam sistem.
Post-condition
  • • Laporan kerusakan dan berkas foto bukti tersimpan di database dengan status Baru.
Basic path
  1. Pengguna membuka menu "Lapor Kerusakan". 2. Sistem menampilkan formulir pelaporan kerusakan. 3. Pengguna memilih fasilitas yang rusak, memilih kategori kerusakan, menuliskan deskripsi kronologi/masalah, dan mengunggah (upload) foto bukti. 4. Pengguna menekan tombol "Kirim Laporan". 5. Sistem memvalidasi kelengkapan isian form dan format berkas foto di sisi server. 6. Sistem menyimpan file foto ke direktori server dan menyimpan data laporan ke database dengan status Baru. 7. Sistem menampilkan notifikasi bahwa laporan berhasil dikirim ke petugas.
Alternative path
  • -
Exceptional path
  • • Pada langkah 5, jika pengguna tidak melampirkan foto atau ukuran file melebihi batas (misal > 2MB) atau format bukan gambar (bukan jpg/png), sistem menampilkan error: "Format file tidak valid atau ukuran file terlalu besar".

Tabel UC-10: Melihat Status & Riwayat Laporan

Use CaseUC-10: Melihat Status & Riwayat Laporan
Pre-condition
  • • Pengguna telah login ke dalam sistem.
Post-condition
  • • Daftar riwayat laporan kerusakan milik pengguna ditampilkan lengkap beserta status dan catatan resolusi petugas.
Basic path
  1. Pengguna membuka menu "Status Laporan Saya". 2. Sistem mengambil seluruh data laporan yang diajukan oleh pengguna tersebut. 3. Sistem menampilkan daftar laporan beserta status penanganannya (Baru, Diproses, Selesai, Ditolak). 4. Pengguna mengklik salah satu laporan untuk melihat detail. 5. Sistem menampilkan detail laporan, foto yang diunggah, serta catatan resolusi/tindakan perbaikan dari petugas jika status sudah Selesai atau Ditolak.
Alternative path
  • -
Exceptional path
  • • Pada langkah 2, jika pengguna belum pernah membuat laporan kerusakan, sistem menampilkan pesan: "Belum ada riwayat laporan kerusakan".
